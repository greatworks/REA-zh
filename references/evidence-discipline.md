# 证据纪律

逆向工程最容易出的错不是分析不出来，而是**把不确定的东西说得太确定**。
这一篇是整套工作法的底线。

## 三分类：观测、推断、未知

每条结论都必须能归到下面三类之一，并且说清它属于哪类。

**观测**——工具实际读到的内容。有证据 ID 可引，可复现。
> 证据 `ev_7f3a…` 显示该函数在偏移 `0x4012c0` 处调用了
> `CreateFileW`，参数 2 的常量是 `0x80000000`。

**推断**——由观测推出、但尚未证实的结论。要写明依据与置信度。
> 依据上述调用与传入的路径常量，推测该分支负责读取用户配置；
> 未验证运行时是否真的走到这里。

**未知**——既不能证实也不能证伪。**未知不等于不存在。**
> 该通道是动态拼接的，静态分析无法确定其字符串值，属未知；
> 不能据此断言「没有这个通道」。

三者混用是这个行业最普遍的污染源。一句「它不联网」如果只是没找到网络调用，
那是未知，不是观测。

## 六条硬规则

1. **静态分析不等于观测到了执行。** 反编译看到的分支可能永远不执行；伪代码
   是分析观测，不是原始源码。
2. **地址与伪代码不是源码。** 还原出的变量名、类型、结构体布局都是推断。
3. **符号名不构成行为证据。** `encryptData` 这个名字不能证明它在加密。
4. **覆盖面不全时只能说未知。** 分析了 60% 的模块，就不能说「整个应用没有
   X」。对等性断言必须建立在完整且可比的集合上。
5. **缺失的证据不等于否定的证据。** 引擎不可用、元数据不支持、超过预算被
   截断——这些都是未知。
6. **不能把客户端截断当成完整结果。** 看到截断提示就换更小的视图或导出证据
   包，不要拿预览当规范 JSON 解析。

## 怎么引用证据

- 引用 `evidence_id`，不要只描述结论。
- 对比类结论引用对比证据的 ID，并列出 JSON Pointer 级别的变化。
- 分页读过的内容，说明读的是哪一页、`coverage` 到哪。
- 同一个结论如果由多条证据共同支撑，全部列出。
- 证据来源不同（静态 / 运行时）时，明确标注类型，不要混在一条里。

## 怎么陈述局限

局限要写具体，不写套话。

差：*受限于工具能力，结果可能不完整。*

好：*本次只分析了 `app.asar` 中 412 个模块里的 96 个；其余模块因堆预算耗尽
未展开，其行为未知。*

差：*动态部分无法分析。*

好：*IPC 通道名由 `atob()` 在运行时解码，静态值为空；该通道的注册与处理器
归属未知。*

## 常见反模式

| 反模式 | 表现 | 正确做法 |
| --- | --- | --- |
| 过度断言 | 「这个应用会上传剪贴板」 | 「观测到它读取剪贴板；是否上传取决于未解析的网络路径」 |
| 缺失当否定 | 「没找到反调试，所以没有」 | 「在已分析范围内未见反调试调用；未覆盖部分未知」 |
| 名字推理 | 「函数叫 `checkLicense`，所以是校验」 | 看调用点、返回值用途与分支走向 |
| 静态当运行时 | 「加载时会执行这段代码」 | 「静态存在该调用；是否执行未观测」 |
| 重跑去猜 | 结果被截断就重跑同一次分析 | 用父证据 ID 取更小的视图，或导出证据包 |
| 借用别人的证据 | 把不同制品摘要的证据拼在一起 | 摘要必须精确匹配才能合并 |
| 无限定词 | 「就是这里」 | 「证据 A 与 B 指向该分支，推断为入口」 |

## 收尾自检清单

提交结论前逐条过一遍：

- [ ] 每个结论都标了观测 / 推断 / 未知
- [ ] 至少关键结论都挂了证据 ID
- [ ] 写了覆盖范围，没覆盖的部分标为未知
- [ ] 没有用文件名、符号名、字符串单独推断行为
- [ ] 没有把静态存在说成运行时发生
- [ ] 对比结论有完整的两侧覆盖
- [ ] 残留未知单独列出来了
- [ ] 原生会话已 `close_binary`，需要的证据包已导出

## 对用户怎么讲

先说结论，再说依据，最后说边界。

> 这个功能的实现路径已经查清：入口在 `app.asar` 的 `main.js`，通过 IPC
> 通道 `export-pdf` 转到原生导出模块（证据 `ev_1a2b…`、`ev_3c4d…`）。
> 具体 PDF 库是运行时动态加载的，静态看不到，这块属未知。
> 目前覆盖了主进程与 3 个渲染进程模块，其余 11 个模块未展开。

三段话，比一段含糊的「基本搞清楚了」有用得多。
